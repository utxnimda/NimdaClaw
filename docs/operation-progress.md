# 通用事务进度

## 使用

- 点击顶部状态提示、业务提示旁的「查看处理详情」或右下角「处理详情」，打开共用窗口。
- 左侧选择任务，右侧显示当前阶段、实际计数、耗时、当前文件 / 目录和时间线。
- 关闭窗口不取消任务，不重复执行；完成或失败后仍可查看记录。
- 未知总量仅展示步骤与计数，不推算百分比。回滚、部分失败、跳过项和连接中断分别明确显示。
- 进度记录保存在当前进程 / 页面内存中，不作为持久审计日志。后端每项保留最多 200 条事件、最多 128 项已完成记录及 30 分钟；前端每项最多 160 条事件、最多 60 项已完成记录。活跃任务不被历史清理淘汰。

## 扩展方式

前端共用 `window.NimdaOperationCenter`，请求经 shell 的 `fetchJson` 自动接入，不需要每个页面建立自己的轮询器。自定义前端操作可使用：

```javascript
const task = window.NimdaOperationCenter.start("处理事务");
try {
  task.progress("正在检查", { completed: 2, total: 5, unit: "项", detail: "当前对象" });
  task.finish("处理完成");
} catch (error) {
  task.fail(error);
}
```

业务提示按钮使用 `data-operation-details`；可增加 `data-operation-prefix="/api/collection-detail"` 打开该模块最近的任务。API 中文名称和通用页面布局集中在 `operation-center.js`，样式位于 `operation-center.css`。

后端服务只需上报实际阶段：

```python
from work_catalog_yaml.operation_progress import report_progress

report_progress("读取数据", completed=3, total=12, unit="文件", detail="当前文件.yaml")
```

无 HTTP 操作上下文时为空操作，CLI 不依赖 Starlette。高频循环需节流，不要逐文件刷日志；不可细分的外部调用报告开始 / 返回。

## 请求与生命周期

- 客户端使用随机 UUID `X-Nimda-Operation-Id`；重复 ID 拒绝，不合并或重复执行事务。
- API 适配层注册排队状态，工作线程内部记录开始 / 结束，并通过 ContextVar 隔离并发事件。
- `GET /api/operations/{operation_id}` 直接读取线程安全快照，不占用磁盘工作队列，返回 `no-store`。
- 所有时间为 UTC ISO 8601，界面转换为本地时间。状态：`queued/running/succeeded/warning/failed/cancelled`。
- 客户端只串行轮询进度，不自动重试业务请求。断线不等于服务端停止，显示「结果待确认」并继续尝试核对。
- HTTP 200 中明确的部分失败 / 跳过同样为 `warning`，断线后只读取进度也不会误报全部成功。
