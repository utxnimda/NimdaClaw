# Media Directory Organizer

这是一个独立 feature 插件。v4 读取 `collection-detail` 作品数据库，对作品父目录中的待整理一级目录逐文件识别作品、压制格式和压制组，再生成可审阅的移动计划。同一个来源目录可以拆成多条路由并写入多个数据库目标；Nimda 的“目录整理”页签默认按单作品目录推导，出现真实歧义时先让用户为整个来源目录确认“单作品或多作品”，只有明确多作品后才展开逐文件选择。页面也支持修正每条路由的目标，以及在数据库没有作品时预览一次完整落地。

## v4 目录与路由规则

1. 作品父目录来自作品 YAML 的 `collection-type.data.path`。物理根目录名只作为初始锚点；一级收集目录唯一命中全库中的另一个完整作品名/别名时，也会把该作品纳入当前根目录候选。因此共享根下的作品不要求互为名称前缀，例如 `グリザイアの果実` 根可以同时包含 `グリザイアの迷宮` 与 `グリザイアの楽園`。
2. 目标压制目录优先严格采用对应 `collectioned[].press_path`，其名称可以完全任意，不要求采用“作品名 + 格式”。数据库未填写 `press_path` 时，`<作品名>_<压制格式>` 仅作为待确认建议；同格式存在多个压制组时追加组后缀。缺少数据库绑定时，快捷方式层会阻止执行并要求先确认 `path/press_path`。
3. 识别单位是文件而不是整个来源目录。文件名命中作品名或配置的 `classification.work_aliases` 后，会路由到对应作品；因此一个混合发布包可以拆到多个作品目标。
4. 目标内布局由“通用分类器 → 压制组派生类”决定：
   - 通用分类为 `Disc`、`CD`、`OP+ED`、`Image`、`Menu`、`CM`、`PV`、`Preview`、`SP`、`Fonts`、`Subs`、`MV`、`Live`、`Others`。
   - `JsumClassifier` 与 `VcbClassifier` 从通用类派生；媒体组注册表中 `classifier_family: VCB` 的发布共用同一个 VCB 分类器，包括 `VA`、`VAF`、`VAL`、`VTL`、`VCDM` 等不以 VCB 开头的组合简称。数据库真实组码和 `press_path` 不会合并。
   - 每个分类文件夹都有独立、可覆写的 `filter_disc()`、`filter_cd()`、`filter_op_ed()` 等虚函数。后续可按压制组、作品名或来源描述只修正一个 Filter，并通过 `super()` 保留通用规则。
   - 分类器只返回“分类 + 分类内相对路径”。父压制目录仍使用完整 `press_path`；分类子目录去掉末尾已确认的压制组，例如 `Little Busters! EX_BDRip(VCBM)\Little Busters! EX_BDRip_CD`。
   - `720p`、`1080p`、`2160p`、`4K` 等以分辨率作为 `press_format` 的发布，如果整条压制只有正片及其同集外挂字幕，并且每集只有一个视频版本，则文件直接平铺在 `press_path` 根目录；字幕不会单独触发 `_Disc_XX`。出现真实多视频版本时仍建立分集目录，出现 `CD/Image/SP` 等其他分类时仍使用完整分类树。`BDRip/DVDRip` 的现有 Disc 分集规则不变。
   - 目录上下文优先于扩展名，分类内的专辑/卷/Booklet 层级会保留；所有 Filter 都未命中的文件进入 `Others`。
5. 当前系列和压制格式只有一个数据库作品、且没有其他已登记作品证据时，未登记的罗马字/别名方括号只作为预览提示，整个来源目录直接继承该作品。存在多个作品证据时，文件进入 `unresolved_files` 并阻止执行；桌面页先提供一次目录级选择，确认多作品后才允许逐文件指定，随后必须重新预览。
6. 一级目录已经是确认或推导出的压制目标、但根部仍有文件或 `CDs/Scans/SPs` 等旧结构时，可以生成受限的原地归类预览：只把文件向该压制目录下的规范分类子目录移动，跳过已经规范化的分类树，并且执行后不删除压制目标本身；确认执行后会清理目标内已经变空的旧子目录。若规范分类树中已有文件、其余只有遗留空目录，则视为已经整理而不是 `empty-source`。重复预览不会再次嵌套已整理目录。
7. 所有计划都保留原文件名。目标已存在、计划内重名、越界路径、符号链接/目录联接、识别歧义或扫描状态变化都会阻止执行。

`press_group` 是数据库组码，目标目录名则由 `press_path` 决定。两者不要求字面相同；例如 Little Busters! 的协作包数据库组码仍为 `VCB`，目标目录按既定命名使用 `(VCBM)`。

## Little Busters! 当前状态

`U:\Little Busters!` 现由数据库独立描述三个作品：

- `Little Busters!`
- `Little Busters! Refrain`
- `Little Busters! EX`

2012 年本篇已有目录保持不变：

- `Little Busters!_BDRip(Jsum)`
- `Little Busters!_BDRip(MW)`

Refrain 与 EX 分别拥有 JSUM 和 VCB 两条 BDRip 记录，四个权威目标为：

- `Little Busters! Refrain_BDRip(Jsum)`
- `Little Busters! Refrain_BDRip(VCBM)`
- `Little Busters! EX_BDRip(Jsum)`
- `Little Busters! EX_BDRip(VCBM)`

v4 会逐文件拆分 `[2013-14][Little Busters! Refrain+EX][BDRIP][1080P][1-21Fin+SP]`，将明确属于 Refrain 或 EX 的 JSUM 文件分别送入两个 JSUM 目标。两个 VCB-Studio 来源也会分别进入 Refrain/EX 的 `(VCBM)` 目标，并按 `_Disc`、`_CD`、`_Image`、`_Menu`、`_OP+ED`、`_Others` 等分类目录组织内部布局。

发布包中的共用 Logo 文件同时包含 Refrain 与 EX 标识，自动识别无法唯一决定其作品归属。它会作为未决文件显示在桌面页；必须人工选择 Refrain 或 EX，再点击“重新预览”生成新计划。未解决该文件前，计划不可执行。

## 桌面版使用与安全确认

打开“目录整理”页签后，应用按插件配置中的 `paths.default_work_root` 重新扫描。先核对每条“来源 → 作品 → 压制组 → 目标”路由，以及逐文件布局和所有未决文件。

修改路由目标、来源目录的作品归属或多作品文件归属会立即使当前计划失效；必须重新预览并取得新的计划 ID。任何实际移动都要依次完成：

1. 确认来源、目标、路由数、文件数、总大小、fallback 数和未决数摘要。
2. 完整输入本次预览的 16 位计划 ID。
3. 通过最终移动确认。

服务端随后仍会重新扫描数据库和文件系统、重建计划，并校验 `acknowledge_move`、预览计划 ID、输入确认码与新计划 ID 完全一致。浏览器提交的移动列表不会被直接执行；任一状态发生变化都会拒绝移动。

执行前和每次移动前都会检查文件状态及路径上的符号链接/目录联接；一级来源目录也不能是联接。移动异常或可捕获的中断会回滚已移动文件。如果某个文件回滚失败，返回明确的 `partial` 状态和原路径、目标路径、失败原因；串联流程会保留已提交的数据库，同时返回数据库文件及历史快照路径供恢复核对，并停止快捷方式创建。此时需先核对和恢复文件，再重新预览。进程被强制终止或断电不保证触发回滚，目前尚无持久化媒体移动日志。

### 数据库没有作品时

普通预览不会再直接报错。页面会显示作品名、日期、类型、国家、发行类型，以及每个来源一级目录的压制格式、组简称和 `press_path`。点击“生成完整预览”只读计算以下三个阶段：

1. 按国家与开始年份新增作品 YAML（例如 `[JP][TVInfo][2014].yaml`、`[KR][TVInfo][2025].yaml`）。
2. 按逐文件分类计划整理所有已分配的来源一级目录。
3. 只为该作品增量创建快捷方式并刷新索引数据库，不清空或重建其他作品的快捷方式。

三个阶段共用一个完整落地确认 ID；执行前必须同时确认数据库写入、媒体移动和快捷方式。数据库写入后若媒体移动失败，新增记录会回滚。媒体移动已经完成但快捷方式失败时，页面会进入“快捷方式待补建”，后续重试只校验数据库和目标目录并创建该作品快捷方式，不会重新扫描来源或再次移动媒体。

### 数据库 path / press_path 需要修复时

若现有作品记录缺少 `path` 或 `press_path`，而目标目录正是本次整理计划将创建的目录，桌面页会生成一个串联预览，不再要求用户先手工建立空目录。服务端会把所选数据库行、格式/组、`press_path`、媒体 assignment 目标和实际待移动文件精确绑定；不存在但不属于当前计划的目标仍会被拒绝。

每个待扫描的一级压制目录都有独立的作品绑定卡片。可以从数据库候选中按 YAML 文件、行索引和内容摘要精确选择已有记录，也可以自由输入作品名；自由输入命中唯一记录时会转换成精确绑定，命中多条同名记录时必须人工选定，完全未命中时则进入本地/Bangumi 候选查找或完整作品信息手填。旧快捷方式及其目标只作为冲突诊断，不能反向决定作品归属，也不会被自动覆盖。

同一作品根可以同时包含“已有记录完整”“已有作品但缺少当前压制行”“完全未入库”等来源。完整落地预览会要求覆盖每个一级目录，并在一次确认事务中合并已有记录、追加新记录、执行媒体归类和创建各自快捷方式；预览阶段不写数据库、不移动媒体。只有用户明确确认某一级目录含多个作品后，目录级绑定才会停用并改为逐文件选择，避免整目录选择与逐文件选择同时生效。

一个物理根同时命中多个数据库作品、但各作品使用不同实体压制目录时，页面仍逐个执行“数据库修复 + 快捷方式”。如果多条播出记录实际共享同一份压制（例如分期播出的两条记录共同指向一个 `Fate／Zero_BDRip`），必须显式启用“共享实体目录”，为每个格式/组选择至少两条精确数据库压制行，并确认共同 `press_path`。预览会分别显示数据库记录数、实体目录数和快捷方式数；媒体只生成和执行一份物理计划，每条播出记录仍按自己的日期生成快捷方式。已存在且完成分类的共同目标允许执行零移动的数据库修复与快捷方式落地。

确认后按“数据库 CAS 修复 → 已预览媒体移动 → 增量快捷方式”执行。媒体移动失败时数据库修复会回滚；移动已完成但快捷方式失败时只进入快捷方式重试，禁止再次执行媒体移动。没有媒体计划的独立数据库修复入口仍保持原规则：`press_path` 必须已经是作品根目录内的普通目录，并且不会移动媒体。

## 命令行

只预览，不移动：

```powershell
.\scripts\organize-media-directories.cmd preview --root "U:\Little Busters!"
```

查看每一个文件的源路径和目标路径：

```powershell
.\scripts\organize-media-directories.cmd preview --root "U:\Little Busters!" --details
```

只有计划为可执行状态时，核对输出中的计划 ID 后才能执行：

```powershell
.\scripts\organize-media-directories.cmd apply --root "U:\Little Busters!" --confirm <计划ID>
```

`apply` 会重新扫描并重新计算计划 ID。文件、大小、修改时间、数据库、分类规则或人工修正只要在预览后发生变化，旧 ID 就无法通过确认。`--json` 可输出 UI/API 可直接消费的结构化结果；多个 `--source "一级子目录名"` 可限制参与规划的来源目录。当前命令行不提供未决文件的交互式作品选择；Little Busters! 的共用 Logo 应在桌面页完成归属选择并重新预览。
